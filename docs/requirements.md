# musubi 要件定義

リポジトリ内の Claude Code SKILL を管理する CLI ツール **musubi** の要件をまとめる。実現方法は [design.md](./design.md) に書く。

- 機能要件は `F-xx`、非機能要件は `NFR-xx`、検証ルールは `E/W/Ixxx` の ID で参照する
- design.md はこれらの ID を引いて、どの要件をどう実現するかを書く

---

## 1. 背景と目的

Claude Code で Agent / Skill / Docs を組み合わせた開発フローを作ると、`.claude/skills/` 配下の SKILL がすぐに増える。数が増えると「どの SKILL がどれを前提にしているか」「仕様違反や壊れた参照がないか」「消してよい SKILL はどれか」を目視で追うのが難しくなる。

musubi の目的は次の 3 つ。

1. リポジトリ内 SKILL の **一覧・検証・作成・改名・削除** を CLI で一貫して行えるようにする
2. SKILL 間の **依存関係を宣言・検出** し、壊れた依存や循環を CI で止められるようにする
3. 依存関係を **グラフで俯瞰** できるようにする（GUI は CLI の解析結果を表示するだけ）

想定規模は 1 リポジトリあたり数十〜100 SKILL 程度（要確認）。

## 2. 用語

| 用語 | 意味 |
| --- | --- |
| SKILL | `SKILL.md` を持つディレクトリ。Agent Skills 仕様に従う |
| 探索ルート | SKILL を探すディレクトリ。`.claude/skills/` に固定 |
| 依存宣言 | SKILL の frontmatter に書く、他 SKILL との関係（`deps.requires` など） |
| 推論エッジ | 宣言ではなく本文から検出した関係（ファイル参照・言及） |
| 診断 | 検証ルールに違反した箇所の報告。error / warn / info の重大度を持つ |

## 3. 前提：Agent Skills 仕様の要点

SKILL は `SKILL.md` を持つディレクトリで、任意で `scripts/` `references/` `assets/` を置ける（agentskills.io の仕様）。musubi が検証の拠り所にする frontmatter の制約は次のとおり。

| フィールド | 必須 | 制約 |
| --- | --- | --- |
| `name` | ○ | 1〜64 文字。小文字英数字とハイフンのみ。先頭・末尾ハイフン不可、`--` 不可。**親ディレクトリ名と一致** |
| `description` | ○ | 1〜1024 文字。何をするか＋いつ使うか |
| `license` |  | ライセンス名または同梱ファイル名 |
| `compatibility` |  | 1〜500 文字。環境要件 |
| `metadata` |  | **文字列→文字列** のマップ。クライアント独自の情報置き場 |
| `allowed-tools` |  | スペース区切り。実験的 |

本文に関する推奨：`SKILL.md` は 500 行以内、参照ファイルは SKILL ルートからの相対パスで、参照の連鎖は 1 段まで。Claude Code はこれに独自の frontmatter キーを追加している。

**重要な前提：仕様には依存関係を表すフィールドが無い。** Claude Code も SKILL 間の依存を解決しない。したがって依存関係は musubi が独自に定義する「人間と CI のための宣言」であり、仕様準拠を壊さない形（`metadata` の利用）で載せる。

## 4. スコープ

**やること（v1）**

- リポジトリ内 SKILL の探索（`.claude/skills/` のみ。Claude Code の SKILL だけを対象とし、他エージェント向けディレクトリは扱わない）
- 一覧・詳細表示・検証（lint）・雛形作成・改名・削除
- 依存宣言の読み取りと解析（欠落・循環・逆引き）、暗黙参照の推論
- グラフのエクスポート（Mermaid / DOT / JSON）
- ローカル GUI での依存グラフ閲覧（閲覧専用）
- CI 連携（終了コード、JSON / SARIF 出力）

**やらないこと（v1）**

- 外部リポジトリやレジストリからの SKILL 取り込み・バージョン解決（将来検討。当面はシンボリックリンクと git submodule で取り込む）
- GUI 上での編集（v1.0 までは閲覧専用。v1.0 の後に見直す）
- SKILL の実行や品質評価（evals）
- `scripts/` 配下のコード実行（解析は静的のみ）
- ユーザー共通の `~/.claude/skills` の管理

## 6. 依存関係の要件

依存は「宣言されたもの」と「本文から推論したもの」を分けて扱う。宣言は CI で強制し、推論は気づきを与えるだけにする。

### 6.1 依存の種類

| 種別 | 由来 | 宣言・検出方法 | 意味 | 検証時の扱い |
| --- | --- | --- | --- | --- |
| `requires` | 宣言 | `metadata` の `deps.requires` | 内容・運用・保守上、相手の存在や内容を前提にしている | 欠落＝error、循環＝error |
| `related` | 宣言 | `metadata` の `deps.related` | 併用すると良い。対称な関係で、片側に書けば両方向から辿れる | 欠落＝warn、循環は許容 |
| `file-ref` | 推論 | 本文のリンクが他 SKILL のディレクトリを指している（例 `../api-review/references/x.md`） | 他 SKILL のファイルに直接依存している | warn。`requires` での宣言を促す |
| `mention` | 推論 | 本文に他 SKILL 名が出現する | 弱い関連 | info。宣言が無ければ「宣言漏れの可能性」として表示 |

### 6.2 `requires` の定義

この SKILL の内容・運用・保守において、別の SKILL の存在または内容を前提とする関係。**実行時の自動ロードや依存解決を保証するものではない。** Claude Code は宣言を読まないので、`requires` を書いても相手の SKILL が一緒に読み込まれるわけではない。musubi が保証するのは「前提にしている SKILL がリポジトリ内に存在し、循環していないこと」だけである。

### 6.3 宣言の書き方

`metadata` は文字列→文字列なので、キーは入れ子にせず `deps.requires` のようにフラットに書く。リストはカンマ区切りで、CLI 引数の `--requires a,b` と揃える。

```yaml
---
name: api-review
description: API変更のレビュー手順。PRにAPI変更が含まれるときに使う。
metadata:
  deps.requires: "repo-conventions,test-writing"
  deps.related: "adr-writer"
---
```

- キーは `deps.` 接頭辞にまとめ、ツール名から切り離す。ツールを改名しても利用者の SKILL.md を書き換えずに済む
- 宣言は SKILL 自身と一緒に移動するので、ディレクトリの移動やコピーで不整合が起きにくい
- 仕様の範囲内なので、他のエージェントや Claude Code はキーを無視するだけで壊れない
- 不採用案：リポジトリ直下の設定ファイルで依存を集中管理する案。一覧性は高いが、SKILL の改名・移動時に設定ファイル側の更新漏れが起きやすい

### 6.4 推論の抑制

推論は設定で種別ごとに無効にできる。個別に抑制する書き方は次のとおり。

| 書き方 | 範囲 |
| --- | --- |
| `<!-- musubi-ignore mention -->` | 直後の 1 ブロック（段落・リスト項目・表など） |
| `<!-- musubi-ignore-file mention -->` | そのファイル全体 |
| `metadata` の `deps.ignore: "mention"` | その SKILL 全体 |

「その行だけ」は、Markdown では段落の折り返し方で意味が変わるので採用しない。

## 7. 検証ルール

| ID | 内容 | 既定 |
| --- | --- | --- |
| E001 | frontmatter が無い、または YAML として不正 | error |
| E002 | `name` の規則違反、またはディレクトリ名と不一致 | error |
| E003 | `requires` の参照先が存在しない | error |
| E004 | `requires` が循環している（自己依存を含む） | error |
| E005 | `name` の重複（探索ルートが 1 つなので通常は起きない。将来ルートが増えたときのために残す） | error |
| E006 | `description` が空、または 1024 文字超 | error |
| E007 | 本文のリンク先ファイルが存在しない（大文字小文字の違いも不一致とする） | error |
| E008 | 探索エラー（読み取り権限が無い、リンク切れのシンボリックリンクなど） | error |
| E009 | `metadata` の値が文字列でない、`deps.*` の値が空・重複を含む、または未知の `deps.*` キー | error |
| W001 | `SKILL.md` が 500 行超 | warn |
| W002 | 参照が連鎖している（SKILL.md → a.md → b.md のように 2 段以上）。`references/sub/x.md` のようなディレクトリの深さは問わない | warn |
| W003 | 許可リスト外の frontmatter キー | warn |
| W004 | SKILL の境界を越えるファイル参照（他 SKILL・リポジトリ外・絶対パス） | warn |
| W005 | `related` の参照先が存在しない | warn |
| W006 | 標準配置外の SKILL.md（探索ルート直下、または 2 階層以上の深さ）。SKILL として扱わない | warn |
| W007 | SKILL へのシンボリックリンクがリポジトリ外を指している（設定で許可したリンク先は除く） | warn |
| I001 | 本文で言及しているが依存宣言が無い | info |
| I002 | どこからも参照されない `references/` のファイル | info |

- **W004 の位置づけ：** Agent Skills の仕様は参照を SKILL ルートからの相対パスで書くよう推奨しているだけで、`../` を明示的に禁止してはいない。W004 は仕様違反の検出ではなく、「SKILL は自己完結させ、他 SKILL に頼るなら `requires` で宣言する」という musubi の運用ルールである
- **有効になる段階：** W004 はパス解決だけで判定でき、E007 と同じ仕組みで動くので v0.1 から有効にする。I001 は言及の推論（F-12）に依存するため、v0.2 で F-12 と同時に追加する
- **終了コードとの関係：** error が 1 件でもあれば失敗とする。warning だけでは失敗にしない（`--max-warnings` で上限を指定した場合を除く）。導入直後に既存 SKILL の warning で CI が落ちるのを避けるため

## 8. 非機能要件

| ID | 区分 | 要件 |
| --- | --- | --- |
| NFR-01 | 性能 | 100 SKILL 規模で `lint` / `graph` が 1 秒程度で終わること（目標値）。計測条件は 100 SKILL、1 SKILL あたり 10 ファイル・平均 200 行、リンク合計数百件 |
| NFR-02 | 移植性 | macOS / Linux / Windows で動作し、1 コマンドで導入できること |
| NFR-03 | オフライン | ネットワーク不要で全機能が動くこと |
| NFR-04 | 安全性 | 既定は読み取り専用。書き込み系（`new` `rename` `rm` `--fix`）は `--dry-run` と差分表示を持つ。`scripts/` は実行しない。GUI サーバーは localhost のみで待ち受け、書き込み API を持たない |
| NFR-05 | 出力の安定性 | JSON 出力に `schemaVersion` を持たせ、並び順を決定的にする（git の差分が読める） |
| NFR-06 | CI 親和性 | 終了コードで成否を返す。JSON / SARIF 出力、色なしモードを持つ |
| NFR-07 | 拡張性 | 検証ルールは ID 単位で有効・無効・重大度を変更できる。ルール追加が 1 ファイルで済む |
