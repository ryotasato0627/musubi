# ADR-0001: 設計判断を ADR で記録する

- 状態: 承認
- 日付: 2026-11-22
- 決定者: プロジェクトオーナー
- 関連: docs/spec/design.md 12 章、`.claude/skills/adr-writer`

## 背景

これまで設計判断は design.md 12 章「設計判断の記録」の表に「論点 | 決定」の 1 行で残してきた。判断が増えるにつれ、次の問題が出てきた。

- 選ばなかった案と、その理由が残らない。後から覆すときに、何を比べて決めたかを追えない
- 開発は Agent が止まらずに進める（dev-cycle）。人間が PR レビューで下した判断を、Agent が後から参照できる形で残す必要がある
- 判断の変更履歴（いつ、何から何に変えたか）が表の書き換えで消える

## 検討した案

### 案 A: design.md 12 章の表だけで続ける

- 良い点: 1 か所で一覧できる。追加の運用が要らない
- 悪い点: 背景・比較した案・影響を書く場所が無い。書き換えると履歴が消える

### 案 B: ADR を正とし、design.md 12 章は索引として残す

- 良い点: 判断ごとに背景と比較を残せる。置き換えで履歴が残る。12 章で一覧性も保てる
- 悪い点: 2 か所を更新する手間がある

### 案 C: ADR だけにして、design.md 12 章を削除する

- 良い点: 更新先が 1 か所になる
- 悪い点: 決定済み事項を一覧で見る場所が無くなる。既存のルール・Skill・Agent が 12 章を参照しており、変更範囲が大きい

## 決定

案 B を採用する。新しい設計判断は `docs/adr/NNNN-<slug>.md` に記録し、design.md 12 章には 1 行の要約と ADR へのリンクを書く。書き方は `adr-writer` Skill に従う。

既存の 12 章の行（2026-11-21・11-22 の判断）は、ADR に書き起こさずそのまま残す。覆すときに、その判断の ADR を新しく書く。

## 影響

- 設計判断を記録するときは `adr-writer` Skill を使う。release-plan・dev-cycle・address-pr はこれに従う
- `承認` の ADR は書き換えず、変えるときは新しい ADR で置き換える
- Claude（Agent）は人間の判断なしに ADR を `承認` にしない。dev-cycle の中では `提案` にして PR で判断を仰ぐ
- 見直す条件: ADR と 12 章の二重管理で食い違いが繰り返し起きたら、案 C への移行を検討する
