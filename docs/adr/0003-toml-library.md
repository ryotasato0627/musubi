# ADR-0003: 設定ファイルの TOML 解析に BurntSushi/toml を使う

- 状態: 承認
- 日付: 2026-11-22
- 決定者: プロジェクトオーナー（v0.1 計画の承認時）
- 関連: F-18、NFR-07、[docs/plans/v0.1.md](../plans/v0.1.md) D2・PR-2

## 背景

`.musubi/config.toml`（design.md 7 章）を読み込む。設定の打ち間違い（未知のキー）を黙って無視すると、ルールの重大度の上書きなどが効かずに気づけない。未知のキーを検出し、使い方・設定エラーの終了コード 2（design.md 5.1）にできる必要がある。

## 検討した案

### 案 A: github.com/BurntSushi/toml

- 概要: Go の TOML ライブラリの定番
- 良い点: 安定している。デコード後に未知のキー（`MetaData.Undecoded`）を取得できる
- 悪い点: 案 B より遅い（設定ファイルは小さいので影響しない）

### 案 B: github.com/pelletier/go-toml/v2

- 概要: 高速で、API が `encoding/json` に近いライブラリ
- 良い点: 高速。厳格モードで未知のキーをエラーにできる
- 悪い点: 案 A との差は musubi の用途ではほとんど無い

## 決定

案 A（BurntSushi/toml）を採用する。未知のキーを一覧として取り出せるため、全部まとめてエラーに出せる。安定性も重視した。

## 影響

- `internal/core/config` は未知のキーがあれば、すべてのキーを示して終了コード 2 にする（PR-2）
- ライブラリの型を config パッケージの外に出さない
- 見直す条件: 設定ファイルが大きくなり性能が問題になったら案 B を検討する
