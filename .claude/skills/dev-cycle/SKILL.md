# Dev Cycle

## Purpose

人間が判断する場面を **計画の承認と PR のレビューだけ** に絞り、それ以外の工程を止まらずに進める。

- **作業量とコストは計画で縛る。** 承認済みの計画（`release-plan` Skill）にある PR だけを、その範囲・やらないこと・修正上限の中で進める
- **品質は受け入れ条件（AC）で担保する。** 受け入れ条件は初回レビューで決め、計画の範囲の中に限る
- **実績を計画に書き戻す。** 見込みとの差が大きければ計画を「要見直し」にする

## 使い方

| 呼び出し | 実行する工程 |
| --- | --- |
| `/dev-cycle` | 計画の中で、依存がすべてマージ済みの最初の「未着手」の PR について 0〜5 を行う |
| `/dev-cycle <PR ID>` | 計画の指定した PR（例 `PR-3`）について 0〜5 を行う |
| `/dev-cycle resume <PR番号>` | 7〜8（人間の判断の反映と確認）。結果を報告して終了する |

計画に無い作業は扱わない。新しい作業は `/release-plan update <版>` で計画に追加してから始める。

## 構成

- **進行役はメインのセッション**（この Skill）。サブエージェントは別のサブエージェントを呼べないため、Agent に進行を任せない
- 各工程は Agent に任せる：`go-dev`（GUI は `web-dev`）、`test-writer`、`reviewer`、`pr-creator`
- **モデルは各 Agent の定義（frontmatter の `model`）に従う。** 開発・修正・テスト（`go-dev` / `web-dev` / `test-writer`）は Opus 5.5、レビューと PR 作成（`reviewer` / `pr-creator`）は Sonnet 5.5。Agent ツールで呼ぶときに `model` を渡さない（渡すと定義より優先される）
- Agent 同士は会話を共有しないので、**作業ディレクトリのファイルで受け渡す**。Agent を呼ぶときは、作業ディレクトリのパス・モード・読むファイル・書くファイルを必ずプロンプトに書く
- Agent を起動するたびに `log.md` に 1 行書く（起動回数を実績として計画に書き戻すため）

作業ディレクトリ：`.claude/work/<ブランチ名の / を - に置換>/`（`.gitignore` 済み。コミットしない）

| ファイル | 書く工程 | 内容 |
| --- | --- | --- |
| `task.md` | 0 | 計画の該当 PR の詳細を写したもの（`templates/task.md`） |
| `dev-report.md` | 1 | 開発 Agent の Output |
| `ac.md` | 2 で作成、4・8 で判定を更新 | 受け入れ条件と判定（`templates/ac.md`）。reviewer が返した `ac.md` 節を **メインが保存** する |
| `review-<N>.md` | 2・4・8 | reviewer が返した `review` 節を **メインが保存** する（`pr-review` Skill の形式） |
| `fix-report-<N>.md` | 3・7 | 修正 Agent の Output |
| `log.md` | 全工程 | 1 行ログ（時刻・工程・起動した Agent・結果） |

## reviewer の起動ルール

レビューの独立性を保つため、reviewer は開発の経緯を知らない状態でレビューする。

- **毎回、新しいインスタンスで起動する。** 2・4・8 のたびに Agent ツールで `subagent_type: "reviewer"` を新規に呼ぶ。以前の reviewer に SendMessage で続きを頼まない。`fork` は会話履歴を引き継ぐので使わない
- **プロンプトに書いてよいのは次だけ**（下のテンプレートどおり）：モード、作業ディレクトリ、ブランチ、マージ先、round 番号
- **書いてはいけないもの**：開発・修正の経緯や意図、`dev-report.md` / `fix-report-*.md` の内容や要約、「〜を直した」「〜は対応済み」などの申告、メインの会話の要約、前回の reviewer の会話
- reviewer が判断に使うのは、`task.md` の計画由来の部分、`ac.md`、差分とコード、`docs/`・`.claude/rules/` だけ（`.claude/agents/reviewer.md` の「独立性」）
- reviewer はファイルを書かない。返ってきた Output の `review` 節を `review-<N>.md` に、`ac.md` 節を `ac.md` に、メインがそのまま保存する（内容を書き換えない）

```text
モード: 初回 | 再レビュー
作業ディレクトリ: .claude/work/<ブランチ名>/
ブランチ: feature/<内容>
マージ先: develop
round: <N>
読むもの: task.md（計画の範囲：要件・やること・やらないこと・完了の目安）、ac.md（再レビューのみ）、git diff origin/<base>...HEAD
```

## フロー

```text
0 準備（計画から PR を選ぶ）→ 1 開発 → 2 初回レビュー（AC 定義）→ [3 修正 → 4 再レビュー] ×修正上限 → 5 PR 作成・実績の書き戻し → 終了
                                                                                    ↓
                                                     6 人間が判断（PR 上でレビュー）
                                                                                    ↓
resume → 7 判断を反映 → 8 再レビュー（人間の指摘を AC に追加）→ [7 → 8] ×修正上限 → push・返信・実績の書き戻し → 終了
```

**0〜5、7〜8 の間はユーザーに確認しない。** 止まるのは「止まる条件」に当てはまる場合だけ。

---

## 0. 準備（メイン）

1. 前提を確認する。満たさなければ止まって報告する
   - `git status --porcelain` が空
   - `gh auth status` が成功する
   - `origin/develop` が存在する（無ければ作らずに報告する）
2. 計画を読む。`git fetch` し、**`origin/develop` 上の** `docs/plans/` から対象の版の計画を探す（`git show origin/develop:docs/plans/<版>.md`）
   - 計画が無い、または状態が「要見直し」 → 止まって `/release-plan` を案内する
   - 計画の「前提作業」に未完了がある → 止まって報告する
3. 計画の状態を最新にする。「PR作成済」「Draft」の PR について `gh pr view <N> --json state` を確認し、マージ済みなら状態を「マージ済」として扱う（書き戻しは手順 6 のブランチで行う）
4. 対象の PR を決める。指定があればその PR、無ければ依存がすべて「マージ済」の最初の「未着手」の PR。条件に合う PR が無ければ止まって報告する
5. `origin/develop` から `feature/<内容>`（バグ修正は `fix/<内容>`）を切る
6. 計画ファイルの該当 PR の状態を「開発中」にし、手順 3 で分かったマージ済みの状態もあわせて更新して、`chore: <PR ID> の作業を開始` としてコミットする
7. 作業ディレクトリを作り、計画の該当 PR の詳細を `task.md` に写す（要件・やること・やらないこと・完了の目安・見込み行数・修正上限・開発 Agent）

## 1. 開発

- `task.md` の開発 Agent（`go-dev` / `web-dev`）を **開発モード** で呼ぶ
- 出力は `dev-report.md`。コミットは `commit-strategy` に従い Agent が行う
- 開発 Agent が「要件・設計の変更が必要」と報告した部分は実装させず、`task.md` の「人間に判断してほしい点」に移す

## 2. 初回レビュー（受け入れ条件の定義）

- 新しい `reviewer` を **初回モード** で起動する（「reviewer の起動ルール」）
- reviewer は受け入れ条件を **計画の範囲の中だけ** で定義し、範囲外の指摘は「範囲外の指摘」に分ける（`.claude/agents/reviewer.md`）
- 返ってきた内容をメインが `review-1.md` と `ac.md` に保存する
- `ac.md` に未達が無ければ 5 へ進む

## 3. 修正

- 開発 Agent を **修正モード** で呼び、`ac.md` の未達項目だけを直させる。出力は `fix-report-<N>.md`
- 未達の項目がテストだけの場合は `test-writer` を使ってよい（プロダクションコードの修正は開発 Agent に任せる）
- 受け入れ条件に無い変更（ついでのリファクタリング、範囲外の指摘への対応など）をさせない

## 4. 再レビュー

- 新しい `reviewer` を **再レビューモード** で起動する（「reviewer の起動ルール」。前回の reviewer は使い回さない）。入力は `ac.md` と差分だけで、`fix-report-<N>.md` は渡さない
- 返ってきた内容をメインが `review-<N>.md` と `ac.md` に保存する
- すべて達成 → 5 へ進む
- 未達あり、かつ修正回数が `task.md` の修正上限未満 → 3 へ戻る
- 未達あり、かつ修正上限に達した → 5 へ進み、**Draft PR** にする

## 5. PR 作成と実績の書き戻し

1. 実績を計画ファイルに書き戻し、`chore: <PR ID> の実績を記録` としてコミットする（「実績の書き戻し」）
2. `git fetch` し、`git merge-tree --write-tree origin/<base> HEAD` でコンフリクトが無いことを確かめる。あれば `origin/<base>` をマージして解消し、4 をもう 1 回実行する（修正回数に数えない）
3. `pr-creator` を呼ぶ。渡すもの：作業ディレクトリ、マージ先、`ac.md`、範囲外の指摘、見送った Non-blocking・Question、`task.md` の「人間に判断してほしい点」、Draft にするかどうか
4. PR 番号を計画ファイルに書き、push する（`chore` コミットを追加）
5. 報告して **終了する**（6 は人間の工程）

---

## 6. 人間が判断（このセッションの外）

人間は PR 上でレビューする。コメントの先頭に `[Blocking]` / `[Non-blocking]` / `[Question]` を付け、design の指摘・「人間に判断してほしい点」には選ぶ案を書く。「人間に判断してほしい点」は ID（`D1` など）で答える（例：レビュー本文に「D1: 案 A」「D2: どちらも採らず現状維持」）。スレッドでもレビュー本文でも会話コメントでもよい。レビュー後に `/dev-cycle resume <PR番号>` を実行する。

## 7. 判断を反映（resume）

1. `address-pr` Skill の **dev-cycle モード** でフェーズ 0〜2（前提チェック・収集・分類）を行う。スレッドだけでなく、レビュー本文・会話コメントの判断（「D1: 案 A」など）も拾う。作業ディレクトリが無ければ（別のマシンなど）、計画ファイルから `task.md` を作り直し、PR 本文の受け入れ条件の表から `ac.md` を作り直す
2. 分類に応じて扱う。**承認を求めない**
   | 分類 | 扱い |
   | --- | --- |
   | fix | 反映する |
   | design（人間が案を選んでいる） | 手順 3 で ADR を記録してから、その案で反映する |
   | design（判断が読み取れない） | 実装しない。スレッド（または PR コメント）に選択肢と推奨を返信し、未解決のまま残す。`提案` の ADR は `提案` のまま |
   | question | 回答を返信する（resolve しない） |
   | skip | 理由を返信して resolve する |
3. **設計判断を ADR に記録する**。人間の判断が 1 つでもあれば、メインが `adr-writer` Skill を呼ぶ（Skill ツール。サブエージェントには任せない）。判断 1 件につき ADR 1 件で、状態は `adr-writer` の「人間の判断と ADR の状態」に従う
   - 判断ごとに `AC-H<n>`「ADR-NNNN が `<状態>` で記録され、README と 12 章に反映されている」を `ac.md` に追加する
4. 反映する指摘を `ac.md` に `AC-H<n>`（由来はスレッド ID）として追加する。**ここで追加するのは人間の指摘だけ**。人間の指摘は計画の範囲外でも受け入れ条件にしてよい（人間の判断が計画に優先する）。後続の PR の範囲や設計が変わる判断なら、計画を「要見直し」にする
5. 開発 Agent を修正モードで呼び、追加した受け入れ条件を満たさせる（ADR の記録はメインが済ませているので、開発 Agent は ADR を書かない）
6. 人間が Approve 済みで、反映する指摘も設計判断（ADR）も無ければ、何もせずに「マージ可能」と報告して終了する。Approve と一緒に判断（「D1: 案 A」など）が書かれていれば、手順 3 で ADR を記録してから進める。**マージは人間が行う**

## 8. 再レビュー（resume）

- 新しい `reviewer` を再レビューモードで起動し（「reviewer の起動ルール」。人間のコメントの経緯や反映内容の説明は渡さない。`AC-H<n>` が `ac.md` に入っていれば足りる）、返ってきた `ac.md` を保存する（未達なら 7-5 に戻る。修正回数は 2〜4 と通算で、計画の修正上限まで）
- 実績を計画ファイルに書き戻してコミットする
- `address-pr` のフェーズ 6（マージ可能性の確認 → push → 返信・resolve）を行う。未達の受け入れ条件に対応するスレッドは resolve しない
- `pr-creator` を **更新モード** で呼び、PR 本文の受け入れ条件の表を最新にし、反映内容のサマリを PR にコメントする
- 結果を報告して終了する（再び 6 へ）

## 実績の書き戻し

計画ファイル（`docs/plans/<版>.md`）の該当 PR の行を、作業中のブランチで更新してコミットする（PR と一緒に `develop` へ入る）。

| 列 | 書く値 |
| --- | --- |
| 状態 | `PR作成済` / `Draft` |
| PR | `#<番号>` |
| 実績行数 | `git diff --shortstat origin/<base>...HEAD` から、生成物・`go.sum`・`testdata` のフィクスチャ・`docs/plans/` を除いた行数 |
| 修正回数 | 3・7 の通算 |
| Agent 起動 | `log.md` の Agent 起動の行数（開発・修正・test-writer・reviewer・pr-creator の合計） |
| 範囲外の指摘 | 件数。内容は計画の「次の候補（範囲外の指摘から）」に追記する |

次のどれかに当てはまったら、計画の状態を「要見直し」にし、「見直しの記録」にきっかけを書く。**このサイクルは止めずに最後まで進める**（次の `/dev-cycle` が 0 で止まり、計画の見直しを促す）。

- 実績行数が見込み行数の 1.5 倍を超えた
- 修正上限に達して Draft PR になった
- 人間の判断で、後続の PR の範囲や設計が変わった
- 「次の候補（範囲外の指摘から）」が 5 件を超えた

## 止まる条件（これ以外では止まらない）

| 状況 | 扱い |
| --- | --- |
| 0 の前提を満たさない（作業ツリーが dirty、`gh` 未認証、`develop` が無い） | 作業を始めずに止まって報告する |
| 計画が無い、「要見直し」、前提作業が未完了、着手できる PR が無い | 作業を始めずに止まって報告し、`/release-plan` を案内する |
| git / gh / Go ツールチェーンが動かず、どの工程も続けられない | その場で止まって報告する |

次の状況では **止まらない**。

| 状況 | 扱い |
| --- | --- |
| 修正上限で受け入れ条件が未達 | Draft PR にし、本文の先頭に未達の条件と原因を書く。計画を「要見直し」にする |
| 要件・設計（`docs/`）・決定済み事項（design.md 12 章・承認済みの ADR）・JSON スキーマ・ルール ID / 既定の重大度の変更が必要、または複数案からの設計判断が必要 | その部分は実装せず、`adr-writer` Skill で `提案` の ADR を書き、PR の「人間に判断してほしい点」に ADR へのリンクと推奨を書く。他の作業は進める |
| コンフリクトが解消できない | Draft PR にし、本文に書く |
| build / vet / golangci-lint / test の失敗が直せない | 受け入れ条件の未達として扱う（Draft PR） |

## 守ること

- 計画に無い PR を始めない。計画の「やらないこと」に手を出さない
- `main` / `develop` に直接コミット・push しない。force push しない。PR をマージしない
- 受け入れ条件は 2 と 7 でだけ追加する（再レビューで増やさない。例外は reviewer が見つけたリグレッション）
- 計画ファイルで更新してよいのは、実績の列・状態・「見直しの記録」・「次の候補」だけ。PR の範囲や見込みは変えない（それは `release-plan` の仕事）
- 最後の報告には、PR の URL、受け入れ条件の達成状況（`n / m`）、修正回数 / 上限、実績行数 / 見込み、Agent 起動回数、範囲外の指摘の件数、人間に判断してほしい点、計画が「要見直し」になったかを含める
