# ADR Writer

## Purpose

「何を決めたか」だけでなく「なぜそうしたか、何と比べたか」を残し、後から判断を覆すときや新しく入った人（と Agent）が経緯を追えるようにする。

## 記録の置き場所と役割

| 場所 | 役割 |
| --- | --- |
| `docs/adr/NNNN-<slug>.md` | 判断 1 件の詳細（背景・検討した案・決定・影響）。**正はこちら** |
| `docs/adr/README.md` | ADR の一覧（番号・タイトル・状態・日付） |
| `docs/spec/design.md` 12 章 | 決定済み事項の索引。1 行の要約と ADR へのリンクを書く |

## ADR を書く場面

- 複数の案から選ぶ設計判断（ライブラリの選定、データ形式、CLI の仕様、レイヤー構成、運用方針など）
- design.md 12 章の決定済み事項を変える、または覆すとき
- `release-plan` の「計画の前に決めること」で決まった設計判断
- `dev-cycle` の resume で、人間が PR レビューで案を選んだ設計判断
- `address-pr` で design に分類され、人間が決めた指摘

書かなくてよいもの：命名や typo のような作業上の修正、要件そのものの追加（それは requirements.md に書く）、一度きりの作業手順。

## 手順

1. **番号を決める**：`docs/adr/` の既存ファイルの最大番号 + 1（4 桁ゼロ埋め）。slug は英小文字とハイフン（例 `0003-deps-in-metadata`）
2. **書く**：`templates/adr.md` の形式で書く
   - 検討した案は、実際に比べた案を 2 つ以上書く（選ばなかった案と理由が ADR の価値）
   - 根拠は docs・要件 ID・計測結果など確かめられるものにする。推測は推測と書く
   - 日本語・常体で書く（`.claude/rules/docs.md`）
3. **状態を決める**
   - 人間が決めた（計画の承認、PR レビューで案を選んだ、会話で明示した）→ `承認`。決定者に人間を書く
   - Claude が提案しただけで、人間の判断がまだ → `提案`。決定者は「提案: Claude」とし、PR の「人間に判断してほしい点」に ADR へのリンクを書く
4. **一覧を更新する**：`docs/adr/README.md` の表に 1 行追加する
5. **design.md 12 章を更新する**（状態が `承認` のときだけ）：表に「論点 | 決定（ADR-NNNN）」の 1 行を追加し、見出し下の日付を更新する。既存の行を変える判断なら、その行を書き換えてリンクを付ける
6. **影響を反映する**：ADR の「影響」に書いた docs・ルール・スキーマの変更を、同じ変更（同じ PR）に含める

## 既存の ADR を変えるとき

- **`承認` の ADR は書き換えない。** 判断を変えるときは新しい ADR を書き、新しい ADR の「関連」に「ADR-XXXX を置き換え」、古い ADR の状態を「ADR-NNNN で置き換え」にする（古い ADR で変えてよいのは状態の行だけ）
- typo や壊れたリンクの修正は書き換えてよい
- `提案` の ADR は、人間の判断が出たら内容を直して `承認` または `却下` にする

## dev-cycle の中で書くとき

- `dev-cycle` は止まらずに進めるので、Claude が自分で設計判断をしてはいけない。判断が必要なら `提案` の ADR を書き、PR の「人間に判断してほしい点」に回す
- resume で人間が案を選んだら、その ADR を `承認` にし（または新しく `承認` の ADR を書き）、design.md 12 章に反映する
- ADR は PR に含める（`docs:` のコミットにする）

## 守ること

- 1 つの ADR に 1 つの判断。複数の判断をまとめない
- 番号は振り直さない。却下・廃止になった ADR も消さない
- 人間が決めていない判断を `承認` にしない
