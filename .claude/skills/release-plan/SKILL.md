# Release Plan

## Purpose

いきなり実装に入らず、**人間が承認した計画の範囲でだけ** `dev-cycle` を回すことで、作業量とコストを制御する。
計画は `dev-cycle` の入力であり、実績を書き戻す記録でもある。

## 使い方

- **plan モードで実行する。** 調査は読み取りだけで行い、計画を ExitPlanMode で提示して承認を得る
- 承認されたら、最初の操作として `docs/plans/<版>.md` に保存する（`templates/plan.md` の形式）
- 計画の承認は、開発サイクルの外にある **人間の確認ポイント** である。ここでは止まって確認してよい（`dev-cycle` の「止まらない」ルールは適用されない）

| 呼び出し | 内容 |
| --- | --- |
| `/release-plan <版>` | 新しく計画を作る（例 `/release-plan v0.1`） |
| `/release-plan update <版>` | 既存の計画を見直す（状態が「要見直し」のとき、または人間の指示） |

## 新しく計画を作る

### 1. 読む

`docs/spec/requirements.md`（特に 9 章のリリース計画）、`docs/spec/design.md`（特に 11・12 章）、`docs/adr/`（承認済みの ADR）、`.claude/rules/`、既存のコード・`docs/plans/`。

### 2. 計画の前に決めることを洗い出す

実装中に「人間に判断してほしい点」として出てくると手戻りになるものを、ここで先に潰す。

- docs の「（要確認）」の項目のうち、この版の範囲に関わるもの
- この版で初めて必要になる決定（例：外部ライブラリの選定、CI の構成、`.golangci.yml` の方針、テストのフィクスチャの構成）
- docs 同士、または docs と既存コードの食い違い

各論点に選択肢と推奨を付け、AskUserQuestion でまとめて確認する。決まったことは計画の「計画の前に決めたこと」に書き、設計判断なら `adr-writer` Skill で ADR を `承認` で書く（記録は計画の承認後、計画の保存と同時に行う）。

### 3. 前提作業を洗い出す

`dev-cycle` は、git リポジトリ・`origin/develop`・`gh` の認証が揃っていないと始められない。足りないものは「前提作業（人間が行う）」に書く。リモートの作成など外部に影響する作業は人間が行う。

土台となる初期設定（`go.mod`・`.golangci.yml`・CI の設定・ディレクトリ構成）は、最初の PR（PR-1）にしてよい。

### 4. PR に分ける

人間が PR を 1 本ずつ、要件と照らして無理なくレビューできる粒度にする。

**粒度**

- 1 PR は、利用者から見て完結した 1 つの機能、または 1 つの検証ルール群を単位にする（例：`musubi list`（F-02）、E003・E004（依存の欠落と循環））
- 変更行数の目安は 400 行程度。生成物・`go.sum`・`testdata/` のフィクスチャは数えない
- リリース計画（requirements.md 9 章）の段階をまたがない。後の段階の機能を先に入れない
- 要件・設計の変更（`docs/`）は、それを実装する PR に含めてよい。実装を伴わない仕様変更だけの PR も可
- 各 PR は `develop` から `feature/<内容>` を切る。前の PR が未マージで後続が依存する場合は「依存」に書く（dev-cycle は依存がマージ済みの PR から着手する）

**各 PR のチェックリスト**

- PR 単体でマージしても、ビルドとテストが通るか
- PR 単体で、要件と照らして動作を確認できるか（`testdata/` や実行例で示せるか）
- 単独では使われない変更（共通部品、依存ライブラリの追加）だけの PR になっていないか
- 機能と無関係な変更（リファクタリング、依存ライブラリの更新、設定変更など）が混ざっていないか
- PR タイトルが「〜と〜」のように複数の目的を並べていないか

各 PR に次を決める。

| 項目 | 決め方 |
| --- | --- |
| 要件 ID | requirements.md の ID。どの PR にも属さない要件が無いこと |
| やること | 触るパッケージ・ファイルと、作る振る舞い |
| やらないこと | 隣の PR に回すもの。**ここが曖昧だと、受け入れ条件で範囲が広がる** |
| 完了の目安 | 要件レベルで確かめること。初回レビューの受け入れ条件の元になる |
| 見込み行数 | 生成物・`go.sum`・`testdata` のフィクスチャを除く。400 行を超えるなら分割を検討する |
| 修正上限 | 既定 3 回。難しい PR だけ増やしてよい（理由を書く） |
| 依存 | マージ順。design.md 1 章のレイヤーの流れに従う |
| 開発 Agent | `go-dev` / `web-dev` |

### 5. 提示と保存

- ExitPlanMode で計画を提示する。PR の数、見込み行数の合計、修正上限の合計（＝最悪の場合の修正回数）を冒頭に書く
- 承認されたら `docs/plans/<版>.md` に保存し、状態を「承認済み」にする
- git リポジトリがあれば、作業ブランチ（`docs/plan-<版>`）でコミットし、`pr-creator` で PR にしてよい。リポジトリが無い場合は保存だけ行い、前提作業の後の最初の PR に含める

## 計画を見直す

`dev-cycle` は、次のときに計画の状態を「要見直し」にし、見直しのきっかけを記録する。

- 実績行数が見込みの 1.5 倍を超えた
- 修正上限に達して Draft PR になった
- 人間の判断（PR レビュー）で、後続の PR の範囲や設計が変わった
- 「次の候補（範囲外の指摘から）」が 5 件を超えた

見直しでは、`docs/plans/<版>.md` の実績と「見直しの記録」「次の候補」を読み、未着手の PR だけを組み替える（マージ済みの PR は変えない）。変更内容を「見直しの記録」に書き、状態を「承認済み」に戻す。

## 守ること

- 計画にない PR を `dev-cycle` で始めない。新しい作業は計画を見直して追加する
- 実績の列（状態・PR・実績行数・修正回数・Agent 起動・範囲外の指摘）は `dev-cycle` が更新する。計画を作る側では空欄にする
- 見込みは控えめにしない。外れた実績は次の見積もりの材料にする
