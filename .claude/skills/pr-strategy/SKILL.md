# PR Strategy

## Purpose

人間が PR を 1 本ずつ、要件（`docs/spec/requirements.md`）と照らして無理なくレビューできる粒度を保つ。

## PR の粒度

- 1 PR は、利用者から見て完結した 1 つの機能、または 1 つの検証ルール群を単位にする（例：`musubi list`（F-02）、E003・E004（依存の欠落と循環））
- 変更行数の目安は 400 行程度。生成物・`go.sum`・`testdata/` のフィクスチャは数えない
- リリース計画（requirements.md 9 章）の段階をまたがない。後の段階の機能を先に入れない
- 要件・設計の変更（`docs/`）は、それを実装する PR に含めてよい。実装を伴わない仕様変更だけの PR も可

## Workflow

1. 変更を上の粒度で分け、PR 計画を作成する
2. 各 PR について、依存関係に従ってマージ順を決める（design.md 1 章のレイヤーの流れ：scanner → parser → resolver → index → analyzers → rules → cli / export）。各 PR は `develop` から `feature/<内容>` を切る。前の PR が未マージで後続が依存する場合は、前の PR のブランチから切り、計画の「依存先」に書く
3. PR ごとに、`commit-strategy` に従ってコミット計画を作成する
4. PR を作成する前に、変更行数を計測する（`git diff --shortstat <base>...HEAD`）
5. 目安を超えた場合は、分割を検討する。分割しない場合は、PR 本文の「備考」に理由を書く

実装中に計画と異なる変更が必要になった場合は、PR 計画を更新してから続ける。

## 計画の作り方

リリース段階をまたぐ PR 計画は `release-plan` Skill で作り、`docs/plans/<版>.md` に保存する（plan モードで作り、人間が承認する）。この Skill はその中で使う PR の粒度とチェックリストを定める。

## 実装から PR 作成まで

承認済みの計画の PR 1 本ずつを `dev-cycle` Skill で進める（開発 → 受け入れ条件の定義 → 修正と再レビュー → PR 作成を止まらずに行い、人間のレビュー後に `/dev-cycle resume <PR番号>` で反映する）。

## PR 計画の形式

```markdown
| # | PR タイトル | 含む機能（要件 ID） | 見込み行数 | 依存先 |
| - | ----------- | ------------------- | ---------- | ------ |
| 1 | feat: SKILL の探索 | F-01, E008, W006 | 約 300 | -  |
| 2 | feat: frontmatter の検証 | E001, E002, E006 | 約 350 | #1 |
```

## PR 本文の形式

```markdown
## 概要
<何を・なぜ>

## 対応する要件
- F-xx / E0xx …

## 受け入れ条件
| ID | 条件 | 判定方法 | 判定 |
| --- | --- | --- | --- |
| AC-1 | … | … | 達成 |

修正と再レビュー: <n> 回

## 変更内容
- …

## 確認方法
- `go test ./...`
- <手で確認したコマンドと出力>

## 人間に判断してほしい点
- D1: <仕様・設計の変更が必要な点>。案 A / 案 B、推奨は案 A（`提案` の ADR があればリンク: ADR-NNNN）（無ければ「なし」）

回答は「D1: 案 A」のように ID で、レビュー本文・スレッド・コメントのどこに書いてもよい。

## レビューしてほしいポイント
- …

## 範囲外の指摘
- <レビューで出たが計画の範囲外として見送ったもの。重大度と場所>（無ければ「なし」）

## 計画との差
- 計画: docs/plans/<版>.md の PR-<n>
- 実績行数 <n> / 見込み <n>、修正 <n> 回 / 上限 <n>、Agent 起動 <n> 回

## 備考
- <400 行を超えた理由、見送った Non-blocking の指摘など>
```

## Checklist

PR 計画の各 PR について、以下を確認する。

- PR 単体でマージしても、ビルドとテストが通るか
- PR 単体で、要件と照らして動作を確認できるか（`testdata/` や実行例で示せるか）
- 単独では使われない変更（共通部品、依存ライブラリの追加）だけの PR になっていないか
- 機能と無関係な変更（リファクタリング、依存ライブラリの更新、設定変更など）が混ざっていないか
- PR タイトルが「〜と〜」のように複数の目的を並べていないか
