# Commit Strategy

## Purpose

AI が大量のコードを生成した場合でも、人間が変更内容を追跡・レビューしやすいコミット粒度を維持する。

## Principle

**1 Commit = 1 Logical Change**

1 つのコミットには、原則として 1 つの論理的な変更だけを含める。

## Workflow

0. 作業ブランチにいることを確認する。`main` / `develop` にはコミットしない（`.claude/rules/git-workflow.md`）
1. 実装を始める前に、コミット計画を作成する
2. 計画した単位ごとに実装し、その都度コミットする
3. 各コミットの前に、ビルドとテストを実行する（Rule 4）
4. 実装中に計画と異なる変更が必要になった場合は、計画を更新してから続ける

実装をすべて終えてから、まとめて 1 つのコミットにしない。

PR の範囲は計画（`release-plan` Skill、`docs/plans/<版>.md`）で決まっている。コミット計画はその PR の範囲の中で作る。

## Rules

### 1. 変更の目的ごとにコミットを分ける

以下のように、変更の目的が異なる場合はコミットを分割する。

- 機能追加
- バグ修正
- リファクタリング
- 既存コードへのテスト追加
- ドキュメント変更（`docs/`）
- 生成物の更新（GUI のビルド成果物など）
- 設定変更（`go.mod` の依存追加単体、CI 設定など）

新しく実装したコードに対するテスト（`testdata/` の追加を含む）は、「テスト追加」として分けず、実装と同じコミットに含める（Rule 3）。

### 2. 関係のない変更を同じコミットに含めない

ある機能を実装するために必要な変更は、同じコミットに含めてよい。

一方で、その機能と無関係なリファクタリングや `gofmt` 以外のフォーマット変更は、別のコミットにする。

### 3. コミットを過度に細分化しない

コミット数を増やすこと自体を目的にしない。以下のような関連する変更は、同一コミットにまとめる。

- 1 つの機能を成立させるために必要な複数ファイルの変更
- 新しい実装と、それに直接対応するテスト・`testdata/`
- データモデル（`Skill` `Edge` `Diagnostic` など）の変更と、`schemas/index.schema.json` の更新
- 検証ルールの追加と、requirements.md 7 章の表への追記

単独では意味を持たない変更（例：使われていない型だけを追加する）は、それを使う変更と同じコミットにする。

### 4. 各コミットでビルドとテストが通る状態を保つ

どのコミットをチェックアウトしても、次が通る状態にする。

```bash
go build ./...
go vet ./...
golangci-lint run
go test ./...
```

`golangci-lint` は必須（`.claude/rules/git-workflow.md`）。`web/` を変更した場合は、そのパッケージのビルドとテストも実行する。

分割によって途中のコミットでビルドが壊れる場合は、分割の単位か順序を見直す。

### 5. コミットメッセージで変更意図を説明する

以下の形式で記述する。

```text
<type>: <変更内容の要約>

<必要に応じて、変更の理由や補足>

Refs: F-04, E007
Refs: #<Issue番号>
```

`<type>` は以下から選ぶ。

| type     | 用途                             |
| -------- | -------------------------------- |
| feat     | 機能追加                         |
| fix      | バグ修正                         |
| refactor | 振る舞いを変えないコードの整理   |
| test     | 既存コードへのテスト追加・修正   |
| docs     | ドキュメント変更                 |
| chore    | 生成物の更新、設定変更など       |

- 対応する要件・検証ルールがある場合は、`Refs:` に ID（`F-xx` / `NFR-xx` / `E/W/Ixxx`）を書く
- 対応する Issue がある場合は、`Refs:` で参照する
- 要約で「〜と〜」「〜および〜」のように複数の目的を並べる必要がある場合は、コミットを分割する

### 6. 大規模な変更はコミット計画を作成してから実装する

変更範囲が大きい場合は、実装前に論理的な変更単位と順序を整理する。順序は、各コミットでビルドが通るように、design.md 1 章のレイヤーの流れ（内側から外側）に従って決める。

例（`lint` に新しい検証ルールを足す場合）：

```text
1. docs: requirements.md 7 章に W008 を追加
2. feat: Parser で <抽出対象> を取り出す（テストを含む）
3. feat: Analyzer で <判定> を行う（テストを含む）
4. feat: W008 ルールを追加（testdata とテストを含む）
5. feat: SARIF のルール一覧に W008 を追加
```

生成物の更新コミットには、手作業による変更を含めない。

### 7. レビュー容易性を優先する

コミットを分割する際は、単純なコード量ではなく、以下を基準とする。

- 変更意図が明確か
- 差分を追跡しやすいか
- レビュー単位として理解しやすいか
- 他の変更と独立して確認できるか
