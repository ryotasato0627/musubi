# テストのルール

- 標準の `testing` パッケージでテーブル駆動にする。テスト名やケース名に要件 ID・ルール ID を入れる（例 `TestE007_CaseMismatch`）
- フィクスチャは `testdata/` に「小さなリポジトリ」として置く（`testdata/<ケース名>/.claude/skills/...`）。1 ケース 1 ディレクトリで、何を検証するかが名前で分かるようにする
- 検証ルールは「診断が出る」「出ない」「境界値」を必ずそろえる
- JSON / SARIF / Mermaid / DOT の出力はゴールデンファイル（`testdata/**/*.golden`）で比較する。更新は `go test ./... -update` のようなフラグで行い、差分をレビューできるようにする
- テストは実際のリポジトリやホームディレクトリに書き込まない。書き込み系・シンボリックリンクのテストは `t.TempDir()` に組み立てる
- OS 差（大文字小文字、パス区切り、シンボリックリンクの作成権限）で結果が変わるテストは、期待値を OS ごとに分けず、設計どおり同じ結果になることを検証する。作成できない環境では `t.Skip` し理由を書く
- ネットワークに出ない。`scripts/` を実行しない
- 実装が仕様と食い違う場合、テストを実装に合わせて曲げない

## よく使うコマンド

- 単一テスト：`go test ./internal/rules -run 'TestE007_CaseMismatch' -v`
- ゴールデンファイルの更新：`go test ./... -update`（更新後は差分を確認してからコミットする）
- 手元での動作確認：`go run ./cmd/musubi lint --root testdata/<ケース名>/.claude/skills`（`--root` はテスト用に探索ルートを 1 つだけ上書きする）
